# ScopeGuard — Product-grade visual direction and quality bar

**Status:** binding design/implementation guidance, not a claim that a screen has been approved or built. Read alongside [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md).

## Product intent

ScopeGuard should feel like a carefully crafted, mature commercial product built by experienced product designers, Flutter engineers and QA specialists—not an autogenerated dashboard. We prioritize clarity, restraint, precision and trust. References such as Linear (information hierarchy), Things 3 (interaction polish) and Revolut (financial clarity) are **principles to study, not screens to copy**.

## Visual principles

1. **Purposeful hierarchy.** One clear focal point per screen; precise alignment, consistent baseline rhythm and readable monetary amounts. Avoid every element competing for attention.
2. **Distinctive, restrained identity.** Lime & Graphite palette and Manrope/Inter are fixed foundations. Lime marks primary action or meaningful emphasis, not every card or label. Use semantic status colors and text/icons together.
3. **Designed content density.** Avoid generic equal-sized KPI cards, giant hero banners in operational screens, excessive pill chips, shadowed card stacks and icon tiles. Use lists, dividers, typographic grouping and whitespace intentionally.
4. **Trustworthy financial UX.** Always show currency, amount, original vs additional scope, and impact on deadlines. Never aggregate different currencies; never hide terms behind decorative UI.
5. **High-fidelity components.** Build a small component inventory with states (default, hover where applicable, pressed, focus, disabled, loading, success, error, empty). Design typography, radii, spacing and motion consistently.
6. **Polish across reality.** Long names, small devices, keyboard, accessibility text scaling, low bandwidth, offline, denied/expired links and dark/light themes are first-class designs.
7. **Motion with intent.** 150–250ms for common transitions where appropriate, predictable easing, no misleading success animations, honor reduced motion.
8. **Originality.** No visual cloning of other products; use references for craft standards only.

## Required workflow for each screen

### 1 — Product designer review (before coding)
- State the user goal, primary action, secondary action, content priority and edge cases.
- Sketch layout and define interaction states for 360, 393, 412dp widths; for approval web include 320, 375, 768 and 1280px.
- Reuse tokens from DESIGN_SYSTEM.md; propose deviations explicitly for approval.
- Show design/reference or detailed spec to owner before implementation where practical.

### 2 — Flutter implementation
- Use feature-first architecture, centralized ThemeData and semantic components; no hardcoded colors, magic spacing or ad hoc duplicate widgets.
- Keep Riverpod/domain logic separate from presentation.
- Respect platform navigation, keyboard insets, touch targets and responsive behavior.

### 3 — Visual QA with evidence
- Run the screen on a real emulator/device when available; capture light/dark screenshots at target widths and with long content.
- Compare against approved reference or specification. Review alignment, typography, spacing, density, hierarchy, states, contrast and truncation.
- Add widget/golden tests for stable states. Golden snapshots are a guardrail, not proof of design quality.
- If emulator/screenshots are unavailable, clearly say **visual QA not performed**; do not claim pixel-perfect implementation.

### 4 — Product polish and acceptance
- Test navigation, keyboard, focus, screen reader, empty/loading/error/offline, destructive actions and server-failure behavior.
- Fix significant visual or UX issues before marking the screen complete.
- PR must include screenshots or an explicit blocker, tests run, known deviations and acceptance checklist.

## Screen-specific priorities

- **Home:** operational clarity, next action and project/request statuses; no decorative finance dashboard.
- **Projects:** scannable project list and clear progress/status without excessive card repetition.
- **Project details:** baseline scope distinct from additional requests, amount and dates prominent.
- **New change request:** guided fields, preview before publish, precise monetary formatting, clear impact.
- **Client approval web:** trust and readability first; exact immutable terms and deliberate accept/reject; no deceptive urgency.

## UI component library and tooling

- **Foundation:** Material 3 adapted to ScopeGuard; not stock-looking default Material.
- **Typography:** Manrope + Inter with explicit type scale and accessibility.
- **Icons:** Material icons first; flutter_svg only for custom vetted assets.
- **Animations:** Flutter native transitions; flutter_animate if useful; Rive/Lottie only for justified identity/illustration.
- **Component workbench:** evaluate Widgetbook once a meaningful component inventory exists.
- **Visual regression:** built-in Flutter golden tests and screenshots; avoid treating snapshots as design approval.
- **Theme:** native ThemeData/ColorScheme first; evaluate FlexColorScheme only for tangible benefit.

All third-party dependencies remain **candidates** until actually installed and verified in pubspec.yaml.

## Quality bar — definition of done

A screen is **not done** until:
- [ ] Screen purpose, hierarchy and approved reference/spec are documented.
- [ ] Light/dark and target screen sizes work without overflow.
- [ ] Monetary and approval information is accurate and explicit.
- [ ] Empty, loading, error and long-content states are implemented.
- [ ] Accessibility labels, contrast, focus, text scaling and tap targets reviewed.
- [ ] Navigation, keyboard and failure recovery tested.
- [ ] Visual screenshots reviewed against spec, or missing emulator evidence explicitly reported.
- [ ] Relevant automated tests run and results recorded.
- [ ] No unapproved visual deviations or copied third-party screens.

## First benchmark screen

**Home / Overview** is the first visual benchmark, but do not mark its design approved until the owner reviews an actual reference/mockup. Deliver:
1. Light and dark variants at 393dp.
2. One populated, one empty and one loading/error state.
3. Component inventory and key tokens.
4. Screen behavior and accessibility notes.
5. Reference screenshot and later Flutter emulator screenshot comparison.

Once approved, make Home the visual quality baseline for subsequent screens.
